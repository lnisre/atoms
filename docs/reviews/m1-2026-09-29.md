## Spec

### P1：真实产物在最新修改未提交时显示已保存，关闭重开会丢数据

**位置：**[真实待办 HTML 第 441 行](../verification/assets/issue-3/production-todo.html#L441)（`isSaving` 分支）及第 451–452 行（旧请求成功即显示“已保存”）；父平台对应 [app-preview.tsx 第 101–105 行](../../src/components/app-preview.tsx#L101)。主要问题发生在生成物的保存逻辑中，父平台目前无法看到尚未发送给桥接层的修改。

**触发条件：**在第一次自动保存未结束时，再添加、完成或删除一条任务。第二次 `persistState()` 只安排 100ms 定时器后返回。第一次保存成功时，产物立即显示“已保存”，平台也因已收到的请求全部完成而显示“应用数据已保存”；此时第二份快照还留在应用内。

**用户影响：**用户按界面提示放心关闭页面，最新修改可能丢失。这是同一预览中的普通连续操作，不涉及规格排除的跨标签并发冲突控制或后台任务。

**对应规格：**#1 User Story 15 要求只在存储成功后显示 saved；Implementation Decisions 要求“存储确认成功后才展示‘已保存’”；User Stories 14、20 要求操作自动保存并能在关闭后恢复。ADR 0002 同样规定写入成功才显示已保存。

**独立复现：**

1. 从生产地址打开全新的专用 Chrome 配置，重放已保留的真实模型 HTML。仅在 `/api/generate` 外部依赖处返回该产物；未修改 HTML，不重新消耗模型额度。
2. 正常添加、完成、删除，刷新恢复、整个浏览器关闭重启和项目列表恢复均通过。
3. 用受控请求保持第一次 IndexedDB readwrite 事务约 550ms，真实事务仍正常提交。保存期间连续添加“关闭窗口第一条”和“关闭窗口第二条”。
4. 应用出现“已保存”、平台出现“应用数据已保存”时立即关闭页面，再打开同一项目。
5. 第一条恢复，**第二条消失**；恢复阶段生成请求为 **0**。另一次复验在显示保存成功时直接读取数据库，确认仅包含第一条。

证据：[集成复现脚本](assets/m1-2026-09-29/rapid-close.mjs)、[关闭前后原始结果](assets/m1-2026-09-29/rapid-close.json)、[恢复截图](assets/m1-2026-09-29/rapid-close.png)、[保存提示与持久状态比较](assets/m1-2026-09-29/independent-behavior.json)。独立 Spec 子代理还用受控 Promise 对原始 HTML 单独复现：[脚本](assets/m1-2026-09-29/spec-artifact-race.cjs)。

保留失败与成功的区别：一次“显示成功后触发 reload”的试验中，导航完成前第二次定时保存赶上，第二条没有丢失；[该记录](assets/m1-2026-09-29/rapid-loss.json)也保留。它不消除已观察到的错误保存提示，也不抵消随后关闭页面得到的明确丢失复现。本报告不声称每次快速操作必然丢失。

**建议修复方向：**生成契约与验证应要求保存期间禁止新修改，或记录 dirty/revision，直到最新快照提交才显示已保存；同时让平台反馈与这个契约一致。补充使用真实产物的连续操作恢复验收，不应只手修一份验收 HTML 后便认为平台问题解决。无需引入 M2、复杂重试或通用并发系统。
