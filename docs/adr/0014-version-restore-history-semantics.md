# 版本恢复后截断后续版本与对话历史

实施规格：[历史项目恢复：代码与数据配对快照、历史截断及单次撤销（Issue #71）](https://github.com/lnisre/atoms/issues/71)。完整浏览器集成验收统一接入 verify-atoms，在本规格实现完成后、交付 PR 合并前执行；各实现 ticket 负责自身改动所需的局部验证。

2026-10-10，用户完成设计访谈并同意收尾规则。本决定记录已确认的产品边界；历史恢复安排在账号云端保存基础验收后实施，当前不启动应用代码改动。

2026-10-10，在版本恢复方案访谈中，用户明确选择 Q3 的 B：恢复到较早版本后，截断该版本之后的版本与对话历史，使项目回到该历史位置继续。此前研究原型采用“保留后续历史、追加恢复记录”的方案，本选择改变了该原型的产品方向；原型仅作为先前方案的实验材料，不代表已确认设计。

用户随后同意 Q1、Q2 的推荐选项：Q1 B，代码和应用业务数据一起恢复到保存点；Q2 A，只长期保留已采用版本，不为每轮未采用候选建立长期历史。项目恢复因此区别于仅切换代码的代码回退。

Q4 已确认采用“历史截断＋常驻撤销提示”。用户担心保留恢复前备份会改变交互形式，因此选择在原工作台呈现操作结果与补救入口：恢复前明确说明代码、数据与历史的变化及可撤销性；恢复后在工作台保留“已恢复到某保存点”和“撤销本次恢复”的常驻提示，刷新后仍可找到，不因短暂提示自动消失而失去入口。被截断版本不继续显示在普通历史列表。

撤销恢复须回到该次恢复执行前的代码、应用业务数据、版本与对话状态，恢复前备份因此不能只包含代码与数据。历史截断不等于立即永久删除可撤销所需内容。

用户同意 Q6 A、Q7 A：只保留最近一次恢复的撤销机会，不维护多层撤销；再次恢复前说明这会替换上一次撤销机会。不设置按小时或天数自动失效的期限，关闭或重开不因此丢失撤销机会。撤销完成、再次恢复等明确操作可以结束或替换它。

Q5 已确认：以“成功采用新的代码版本”为结束撤销机会的边界。浏览、刷新、业务数据保存、生成候选或放弃候选不自动使其失效；生成或保存进行中暂不可执行撤销。存在未采用候选或恢复后业务数据变化时，撤销前在同一确认中说明会舍弃这些内容，不合并到恢复前状态。采用区域提前说明“采用后将结束本次恢复的撤销机会”；只有采用事务成功提交，才一并结束撤销资格并清理对应备份，采用失败则保留。此决定细分了最初 Q5 的二选一，不等于“任意新修改都失效”或“采用后仍长期可撤销”。

该决定依据用户提出的交互直觉与实现复杂度要求，利用已有“候选试用 → 明确采用”的产品边界。当前应用的数据桥只接收统一保存请求，不能据此可靠区分主动操作、自动保存或初始化写入；因此不让任何业务数据保存自动结束撤销。恢复前完整备份与原子切换是既定方案本来就需要的能力，沿用它处理后续数据的舍弃，不引入字段级合并或多层撤销。

用户同意 Q8 B、Q9 A：历史版本默认配对其被下一版本替换前最后保存成功的业务数据，而不是刚开始使用时的数据。例如 V1 开始时有 10 条记录，采用 V2 前已有 100 条，恢复 V1 使用该次替换前的 100 条；不包含后来在 V2 下新增的数据。历史入口需同时标明代码版本与保存时刻，使用“采用 V2 前保存”等说明，避免把代码版本等同于任意时间的数据状态。

首版只在版本变化的关键时刻自动保存，不提供手动创建项目快照，不承诺同一代码版本使用期间任意时点的数据恢复。采用前配对保存旧代码与当时已提交的数据，是实现上述恢复语义的必要条件；未保存输入不在恢复范围内。首次正式版本及功能启用前旧项目的基线需如实标注实际保存时刻，不能补造更早历史。

用户在上一轮访谈中同意 Q10 A、Q11 A：不自动删除较早历史，保留所有未被恢复操作截断、也未被用户主动清理的历史；空间不足时停止本次采用或恢复，保留操作前完整状态并提示处理存储问题后重试，不能出现新代码已采用但旧版本未保存的部分成功。后续 Q14 确认提供用户主动清理旧保存点的入口。

存在未采用候选时，可以查看历史，但执行项目恢复前须先明确采用或放弃候选，不在恢复确认中顺带放弃。撤销恢复找回的是恢复前的正式项目，不负责找回此前已经放弃的候选。此规则不改变 Q5 中“恢复后新产生候选时如何撤销恢复”的约定。

用户同意 Q12 A、Q13 A、Q14 A：历史副本试用为可选步骤，查看版本说明和数据保存时刻后可直接进入恢复确认；试用操作不写入正式项目、不改变保存点，也不作为实际恢复的数据来源。恢复确认展示目标代码版本、数据保存时刻、将移除的后续版本与对话，并明确当前业务数据会被替换；首版不承诺逐条业务记录或字段差异对比，避免对任意应用数据结构作不可靠的解释。

首版提供手动清理旧保存点的能力，由用户选择并明确确认永久放弃这些保存点的恢复能力。用户在收尾时确认：清理只删除快照，保留对应修改记录和对话，并标注“已清理，无法恢复”；当前项目、有效撤销备份及完成撤销所依赖的内容均受到保护，不允许清理。这使用户可以主动释放容量，同时保留项目演变的说明，并保证可见的撤销入口仍然有效。此决定不授权自动删除历史。

交付顺序采用 Q15 的云端优先方向：先完成并验证账号归属、项目与正式业务数据的云端保存、多设备旧写入保护及失败时的完整状态保留，再实现历史恢复。与 [ADR 0015](0015-account-owned-cloud-projects.md) 一致，登录与云端保存独立交付；后续历史快照与撤销状态统一归账号并存于云端。本轮先完成设计，不先建设一套待迁移的浏览器本地历史恢复。这能避免重复建设保存与冲突处理机制，代价是历史恢复等待云端保存基础验收。

本轮产品设计访谈完成。后续在上述边界内细化界面和实现；若发现必须改变这些规则的约束，再重新讨论对应决定。旧研究原型仍采用早期保留后续历史的方案，尚未同步本决定，不能作为本方案的验收依据。功能启用前未保存的历史快照不能事后补回。

本决定针对 [ADR 0004](0004-m2-conversational-updates.md) 留待后续的恢复功能；当前仅更新设计文档，不改变现有 M2 的行为，不修改应用代码、现存用户数据或历史记录。设计确认不表示功能已实现或验收通过。
